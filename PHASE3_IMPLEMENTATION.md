# SignTalk Phase 3: Camera Recognition Status

## Implemented

The existing camera and MediaPipe Holistic path is preserved. Camera YUV420 and BGRA frame conversion is isolated in `CameraFramePreprocessor` and covered by tests. Holistic now requests face blendshapes. Results are converted into fixed-order frame features for face mesh, facial blendshapes, image/world pose, and image/world landmarks for both hands. A bounded timestamped buffer tracks gaps and missing detections. A pause-based activity segmenter marks candidate utterance boundaries and rejects interrupted/short segments; its thresholds are provisional and must be calibrated against real signer data.

`AslContinuousRecognitionModel` is the adapter contract for a local temporal model. The checked-in `assets/models/asl_recognition.json` is explicitly unavailable: there is no model path, license, architecture, training dataset, class vocabulary, or reviewed sentence map. The camera still tracks locally, but it never emits fabricated glosses, English text, or confidence. The decoder only emits an English sentence for a complete high-confidence gloss sequence with an exact reviewed mapping. Unknown signs, unsupported sequences, low confidence, and incomplete signing are withheld.

The app feature schema is `signtalk.holistic.2582.v1`: 2,582 ordered values per frame (including derived wrist direction, palm normal, and hand-motion energy), 8–64 frame temporal input, and 30 fps. The adapter now checks task, ASL language, continuous sentence translation, exact feature-schema identifier as well as dimension, an offline Flutter runtime, model path, license, calibrated confidence, and a 64-character SHA-256 before considering a manifest compatible. Equal vector width alone is not accepted. The current manifest correctly fails those checks because no model/runtime is installed.

## Setup and exact remaining requirements

No setup is needed for offline landmark tracking and temporal buffering. To enable ASL sentence output, supply a redistributable continuous-ASL checkpoint or train/release one under an app-compatible license; document dataset and signer-independent splits; provide Android-compatible offline runtime weights; match the checkpoint's exact preprocessing/features; include a reviewed ASL gloss-to-English decoder or direct sentence output; calibrate unknown/blank and confidence rejection; and evaluate using independent genuine ASL videos with reviewed English ground truth. Device-level camera inference has not been visually or performance-verified in this environment.

Phase 3 is **not complete**. The camera tracking and adapter pipeline are implemented, while real ASL recognition and sentence output remain unavailable until those assets and evaluation inputs exist.

### Current research update (2026-11-18)

The newly published sign-language-bridge checkpoint is the closest current released ASL sentence model found. Its public card supplies actual adapter weights, Apache-2.0 terms, training description, and inference code. It still cannot be honestly wired into this app: the expected input is sampled RGB video with pose crop/contrast adjustment/keypoint overlays, while this Flutter model adapter accepts the separately defined Holistic feature sequence; converting between them would require sending camera frames into a 2B vision-language stack, not reshaping the 2,582 landmark values. The documented inference stack is Python PyTorch/Transformers and has no Android runtime. Its WER is 112.51% on a custom split, and the authors warn output can be fluent yet wrong. Therefore no checkpoint was downloaded or bundled, and no predictions were made.

An adapter guard and regression test were added so a future model cannot pass integration checks based only on matching feature dimensions. It requires an explicit schema ID, sign-language/task declaration, Android-capable offline runtime declaration, model/license metadata, calibrated confidence declaration, and checkpoint SHA-256. This is a contract guard, not an inference engine or a model. The adapter tests and analyzer were rerun after the change; all 22 project tests pass.

### Integration path decision and training/export plan

The current app model adapter receives exactly `List<TemporalLandmarkFrame>`: each frame carries timestamp, 2,582 ordered float features under `signtalk.holistic.2582.v1`, visibility flags, per-hand coordinate/orientation arrays, and motion energy. A compatible inference adapter must return actual model output through `AslRecognitionModelOutput` / `AslModelHypothesis`, including sentence or gloss sequence, calibrated confidence and completion status. It must not fabricate values. The manifest requires 8–64 frames at the declared 30 fps and rejects mismatched schema identifiers.

Runtime assessment: ONNX Runtime Mobile can be a viable Android execution backend for a supported exported graph, but does not make an incompatible research checkpoint compatible by itself. TensorFlow Lite has the same limitation; no candidate with verified weights, compatible feature preprocessing, redistribution rights and sentence-level ASL output was found for validated conversion. No runtime dependency was added. The prior `sign-language-bridge` checkpoint takes RGB video and a 2B Qwen3-VL base, so its documented stack cannot fit the current landmark adapter and has no demonstrated offline Android path. Its exact installed-device storage/latency/peak-memory are therefore not measured. The 4.5M/17.9MB ONNX Saudi model is a useful size comparison but recognizes Saudi Sign Language glosses under CC BY-NC-SA 4.0, not ASL English sentences; it is excluded.

Recommended experiment scaffold: (1) obtain How2Sign or another ASL video/English corpus under documented research/use terms, preserving its official signer-independent train/validation/test split; separately record any app redistribution restrictions; (2) run the exact app Holistic version and normalization on each video, export versioned 2,582-feature sequences plus masks/timestamps, and audit parity on saved sample frames; (3) train a temporal encoder plus direct English decoder or supervised gloss CTC plus reviewed ASL-to-English decoder, with signer-held-out evaluation and unknown/blank handling; (4) export the trained graph to ONNX, verify numerical parity against the training framework, quantize only after parity checks, and benchmark Android CPU/NNAPI load time, per-window latency and peak memory; (5) calibrate confidence and rejection on a separate signer-independent validation set; (6) evaluate final WER and exact sentence accuracy on untouched, genuine recordings. Do not use synthetic labels or claim model quality from training-set fit. This is a plan only; no training/evaluation corpus or checkpoint is currently in the workspace.

No Android device/emulator inference was verified in this turn. No independent ASL recordings and references are installed, so local WER, sentence accuracy, latency, memory, and rejection performance remain unavailable.
